# Adaptive Runtime 验证报告：判定器可信度、统计功效与实测数据

> 本文回答两个问题：
> (1) 三层演化能力（L1 / L2 / L3）为何按阶段启用，而非一次性全部打开；
> (2) 依据什么判定该闭环确实提升了任务质量，而不只是把代码跑通。
> 所有数字均来自本仓库实测；不可验证的部分在 §8 明确列出。

---

## 1. 分层启用策略

| 层 | 改动对象 | 可枚举性 | 误判风险 | 默认状态 |
|---|---|---|---|---|
| **L1 参数** | `.env` 数值（迭代预算、解析重试、再规划门槛） | 完全可枚举（4 个真实参数，每个 2–3 档） | 低：改的是数值，行为差异可归因 | 开启 |
| **L2 提示** | `prompt.py` 的角色 / 系统提示（单处、≤15 行） | 半可枚举（模板库，当前 4 条补丁） | 中：提示改动同时影响多个环节 | 由 `ADAPTIVE_MAX_EDIT_LEVEL=2` 开启 |
| **L3 结构** | 控制流（replan 空转上限、观测窗口、计划增长上限） | 可枚举但**语义耦合** | 高：改动会混淆「因果」与「实现缺陷」 | 由 `ADAPTIVE_MAX_EDIT_LEVEL=3` 开启，当前不启用 |

**L3 暂不启用的理由是验收能力，而非实现进度。** 控制流改动一旦引入回归，无法区分「该方向错误」与「实现被改坏」。在 L1 / L2 的处理曲线稳定之前启用 L3，得到的结论不可归因。这与灰度发布中「先小流量验证再放量」的逻辑一致。

## 2. L2 接通情况与对既有结论的更正

**对上一版结论的更正**：此前曾表述「L2 代码路径已就位，打开即生效」。该结论不成立——实测打开后产出的候选仍全部属于 L1。原因是 `SEARCH_SPACE` 中没有 `level=2` 条目，`max_edit_level=2` 仅抬高了准入阈值，而阈值之上没有可选项。

本轮已补齐：

- `proposer.PROMPT_PATCHES`：4 条针对真实失败模式的提示补丁（每条 5–6 行 diff）
- 锚点在**导入期**校验必须恰好出现一次；写错直接报错，不允许「静默不生效」（否则候选 ΔQ ≈ 0，会被记为「该假设无效」，把无效证据写入台账）
- `probe.apply_prompt_patch()`：只作用于候选沙箱、只打一次、打完后做语法编译检查
- `round --level 2` / `benchmark --level 2`：可单独实测指定层级

当前 L2 的实测结果（同一失败模式，仅切换开关）：

```
L1 模式（max_edit_level=1）：3 个候选，全部 L1
L2 模式（max_edit_level=2）：6 个候选
  - AGENT_MAX_ITERATIONS (L1)
  - AGENT_PARSE_TRIES (L1)
  - prompt.py::coder.stop-on-repeat (L2)          ← 新增
  - prompt.py::coder.save-skeleton-first (L2)     ← 新增
  - AGENT_REPLAN_ARTIFACT_MAX (L1)
  - prompt.py::supervisor.keep-done-steps (L2)    ← 新增
```

第四条补丁 `prompt.py::coder.require-sources` 绑定 `REVIEW_FAILURE` 模式；当前失败样本以 `recursion` / `truncated` / `exception` 为主，故该补丁未进入候选集。补丁模板与失败模式的绑定关系是显式的（`PROMPT_PATCHES[*].taxonomies`），样本覆盖到对应模式后即自动可提议。

补丁生效的硬证据：候选沙箱内 `prompt.py` 新增 5 行，基线沙箱为 0 行，且语法校验通过。

## 3. 三层验证

### 3.1 第一层：判定器是否具备分辨力（受控对照，零 LLM 成本）

这是唯一能在不产生模型调用成本、不依赖人工等待的前提下证伪整套机制的实验。`selftest` 共 9 项，其中四项对照为核心：

| 检查 | 期望 | 证明内容 |
|---|---|---|
| `negative_control_zero`（**零改动**） | `REJECT/within_noise` | δ 计算正确，未凭空产生差异 |
| `negative_control_worse`（**故意变差**） | `REJECT/contract_floor` | 比较方向未反转 |
| `sensitivity_base_vs_base`（**base vs base**） | `REJECT/within_noise` | 同名两臂不会「自然涨分」 |
| `positive_control_good`（**真实改进**） | `ACCEPT/VALIDATED` | 门不是恒关状态 |

**该层优先级最高**：一个恒 REJECT 的 Gate 看似严谨、实际无用；一个恒 ACCEPT 的 Gate 会破坏整个系统。只有「能拒也能收」才说明判据具备分辨力。

当前状态：**9/9 通过**。

### 3.2 第二层：单个改动是否有效（配对 t + 噪声门限）

```
δ = t_{1−α/2, n−1} · sd(Δ)/√n
ACCEPT(VALIDATED) ⟺ mean(Δ) > δ
```

本轮修复了两个会导致结论失真的统计缺陷：

1. **以重复次数虚增自由度。** 原实现将 n 取为 `(task, rep)` 对数，导致「1 个任务跑 4 次」被当作 n=4。而 temp=0 的后端会使 4 次结果完全相同 → `sd=0` → `δ=0` → **任何正收益都会被判为显著**。现改为**先按任务聚合再检验**，n 为任务数，方差取任务间方差——这才是「换一个新任务是否仍成立」的正确估计。
2. **`n_tasks=1` 时 δ=0，均值大于 0 即过门。** 等价于「用单个任务单次执行验收任何改动」。现 `n_tasks < 2` 直接判 `INCOMPLETE_EVIDENCE`，因为单任务证据在原理上无法回答「是否普遍有效」。

### 3.3 第三层：多轮演进是否成立（benchmark）

`benchmark` 连续执行 k 轮完整闭环，输出两项结果：

- **ΔQ 序列**：第 1..k 轮各自的配对增益。全为正且逐轮过门即为有效；自第 2 轮起全部为 `WITHIN_NOISE` 表示搜索空间或诊断信号已耗尽（该结论本身同样有价值）。
- **holdout 平稳性**：在**未 promote** 的轮次中，留出任务上的 base Q 必须保持平稳。若其自行上升，说明存在泄漏（holdout 参与了诊断 / 提案 / 经验写入），此时所有「提升」均不可信。

```bash
# 真实模式（产生 LLM 成本，执行前先看成本预估）
python -m adaptive_runtime.run_adaptive benchmark --rounds 3 --n 4 --limit 12 --holdout 0.3

# 管线自检模式（不产生模型成本，使用受控模拟轨迹）
python -m adaptive_runtime.run_adaptive benchmark --fake --case good --rounds 3 --n 2 --limit 6
```

模拟模式的输出示例：

```
3 轮完成：ACCEPT 3 / REJECT 0 / SKIP 0
ΔQ 序列：['+38.1', '+38.1', '+38.1']
holdout 平稳（drift=+0.00），未 promote 期间无泄漏或漂移
```

模拟模式仅用于验证管线连通性，其数值不构成有效性证据（见 §7）。

### 3.4 第三层的真实成本（实测）

以 `replay.json` 中的 `REP-001`（真实研报任务）执行一次基线臂：

| 指标 | 实测值 |
|---|---|
| 运行时长 | 1108.6 s（18.5 分钟） |
| LLM 调用次数 | 58 次 |
| Token 消耗 | 649,632（55 次为真实 usage，3 次因连接异常降级估算） |
| 参与 agent | `supervisor` 5 次 / `crawler_agent` 13 次 / `code_agent` 40 次 |

按该单价推算：

| 规模 | runs | token | 墙钟 |
|---|---|---|---|
| 最小统计可行（2 轮 × 2 任务 × 2 臂） | 8 | ≈ 480 万 | ≈ 2.5 小时 |
| 具备检出能力（3 轮 × 4 任务 × 2 臂） | 24 | ≈ 1400 万 | ≈ 8 小时 |
| 方案建议的 n=8（3 轮 × 8 任务 × 2 臂） | 48 | ≈ 2900 万 | ≈ 16 小时 |

**结论**：第三层无法「顺手执行」，必须排期（建议夜间）。这也解释了为何第一、二层必须做扎实——它们是日常迭代中唯一可承担成本的校验手段。

> 说明：单 run 60 万 token 是本仓库真实研报任务（多轮抓取 + 报告生成）的量级，与千级 token 的连通性测试相差两个数量级。以连通性测试推算成本会严重低估。

## 4. 前置条件：Q 必须不可刷

若分数可被刷，则「ΔQ 显著为正」这一结论本身失去意义——闭环会精准地学会刷分，且效率高于人工。审计发现两条通道：

### 通道 1：空壳交付物

`pick_report` 原先仅按「体积最大的 .md」选择。一次真实运行将闲聊内容存为 md，得到 `E=0 / C=1 / Q=70`——**一个未产出任何实质内容的 run 获得 70 分**。

修复：报告需同时满足最小体积（`ADAPTIVE_MIN_REPORT_BYTES`，默认 1200 字节）与结构分（体积 / ≥3 个标题 / 有表格或列表 / 有结论段，各占 1/4），结构分作为 C 的乘数。不合格产物标记 `thin_deliverable`，按「无报告」处理。

### 通道 2：削减工作量换取高分

```
A = 通过 gate 的 step / 计划 step
C = 1 − (截断+兜底+缺失产物) / (计划产物+1)
```

两个分母均来自 Agent 自身计划。因此「将计划压缩为 1 步并通过它」可得 `A=1.0, C=1.0`，Q 的下限为 70——**规划越少，分数越高**。

修复分两层：

- **打分层**：结构分与计划无关，约束「产物是否像一份报告」；
- **判定层（关键）**：`plan_undercut` —— 若某任务上 `cand_planned < base_planned × 0.6` **且** `A` 反而上升，记为刷分；≥50% 的配对出现该模式即 `REJECT`。仅拦截「变短 **且** A 上升」这一组合，避免误伤「因效率提升而减少步骤」的真实改进。

## 5. 真实 run 的分数分解

### 5.1 基线臂

`REP-001` 完整执行结果：

```
耗时 1108.6s（18.5 分钟）   tokens 649,632   真实 usage 占比 95.1%
Q = 73.02   A = 1.00   E = 0.1007   C = 1.00   planned = 6 步
产物 14 个 / 缺失 0 / 报告结构分 1.0
证据：268 个关键数字，其中 27 个带来源
```

该分解说明三点：

1. **A 与 C 已满分**，Q 的 27 分差距几乎全部来自 E（证据率 10%）。按权重，将 E 由 0.10 提升至 0.60 可使 Q 由 73 升至 88——这是当前唯一有意义的改进方向。
2. **诊断层无法识别该方向**。`diagnosis` 仅从 trace 读取 `kind=recursion/truncated/exception`，这些均属「失败」；E 低不是失败，而是质量维度。因此提案层原本不会针对证据率提出改进。这是真实的结构性缺口，本轮补充了对应候选（`prompt.py::coder.require-sources`，L2，要求每个数字就地标注来源），但它属于**人工先验**，并非闭环自行发现——此点必须明确记录。
3. **A=1.0 不构成刷分**。planned=6 属正常规模（非压缩至 1 步），且实际产物 14 个 > 计划产物 4 个。

### 5.2 同一任务的两次运行相差 24 分

在 `REP-001` 上执行 L2 提示补丁的真实两臂对比（1 任务 × 2 臂）：

| 臂 | Q | A | E | C | planned | tokens |
|---|---|---|---|---|---|---|
| base（原提示） | 48.57 | 0.571 | 0.000 | 1.000 | 7 | 405,894 |
| cand（+`stop-on-repeat`，5 行） | 60.34 | 0.857 | 0.139 | 0.667（有 truncated） | 7 | 501,513 |

ΔQ = **+11.77**，补丁确认应用（`added: 5`）。判定结果：

```
REJECT(incomplete_evidence) @ min_tasks     n_tasks=1, need=2
```

**必须拒绝的理由**：同节的基线 run 在同一任务、同一份代码上取得 `Q=73.02`（A=1.0 / E=0.10）。即同一任务两次运行，Q 由 73.02 降至 48.57，相差 24.45 分。该量级的波动主要来自 A（计划 7 步中若干步是否过门存在随机性）。

由此可反推噪声门限量级：若单次运行 σ ≈ 24，则 n=8 时 `δ = t(0.975,7)·24/√8 ≈ 2.365 × 8.49 ≈ 20 分`。**即：小于 20 分的提升在 n=8 下不可检出。** ΔQ=+11.77 恰好落入该盲区——仅以一个任务的结果宣告「补丁有效」，等同于把噪声当作结论。

这也解释了方案将 n 默认设为 8 的原因，以及 `min_tasks` 这道门必须存在的理由。

### 5.3 统计功效与样本量

按 `required_n(sd, effect, power=0.8, α=0.05)`：

| 配对差值 sd | 检出 ΔQ=5 | ΔQ=10 | ΔQ=20 | ΔQ=30 |
|---|---|---|---|---|
| 6.0（原配置假设） | n=12 | n=3 | n=2 | n=2 |
| 15.0（现配置，保守折中） | n=118 | n=18 | n=5 | n=3 |
| 24.5（实测单 run 波动） | n=188 | n=47 | n=12 | n=6 |

对应成本（单 run 65 万 token / 18 分钟，每个配对 2 个 run）：

| n | token | 墙钟 |
|---|---|---|
| 8 | 1000 万 | 4.8 小时 |
| 18 | 2300 万 | 11 小时 |
| 47 | 6100 万 | 28 小时 |

**结论：该体系仅对大改进敏感。** 能通过门限的改动需带来 ≥20 分（n=8）至 ≥10 分（n=18）的真实提升。`stop-on-repeat` 这类 +11.77 的候选，要么将 n 提升至约 40，要么不应对其验收抱预期。

这是研报类任务产出方差大的必然结果，而非实现缺陷。原配置假设 sd=6.0 会使 `required_n` 低估约 `(15/6)² ≈ 6` 倍，即「以为 n=8 足够，实际需 n=40+」。现已将 `ADAPTIVE_SD_TARGET` 默认值调整为 15.0，并在 `validate()` 中增加启动告警：**当 n 过小导致 δ>20 分时直接提示「本轮不具备检出能力」**，避免无效的长时间运行。

## 6. 诊断层的质量缺陷通道（缺陷修复记录）

### 6.1 被发现的盲区

诊断层原有信号只有硬失败：`kind=recursion / truncated / exception`，
外加 gate 反复 reject 与 replan 空转。这带来一个结构性盲区：

> 一次「每步都 PASS、正常收尾、报告已落盘」的 run，会被判成 `UNKNOWN / 无失败信号`。

而 §5.1 的实测数据说明最大失分项恰恰在此：A 与 C 已接近满分，
27 分差距全部落在 E（268 个关键数字仅 27 个带来源）。只看硬失败，
闭环会认为这批 run 无改进空间，因此永远不会提出「给数字加来源」这类候选。

修复方式：新增 `Taxonomy.QUALITY` 两类（以框架无关的通用字段判定，不绑定业务域）—

| 类别 | 判定字段 | 含义 |
|---|---|---|
| `EVIDENCE_FAILURE` | `Score.E` < `evidence_floor` | 成品中的量化断言缺来源 |
| `COMPLETENESS_FAILURE` | `Score.C` < `completeness_floor` | 计划产物缺失 / 截断 / 兜底 |

`classify()` 增加可选 `score` 参数；不传时行为与首版完全一致，保证历史产物可复现。
同时 `proposer` 中 `prompt.py::coder.require-sources` 改映射到 `EVIDENCE_FAILURE`
——此前它挂在 `REVIEW_FAILURE` 下，而诊断永远不会因 E 低产出该类别，
**这条补丁实际上从未被闭环自动触发过**。

### 6.2 修复过程中踩到的两个坑

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 复盘历史日志时报出「完整性 0.50」缺陷 | 日志还在、产物已被外部清理；E 按 live 语义记 0，被误当成「质量差」 | 统一前提：仅当 `detail["report"]` 存在（确实读到成品文本）时才判质量缺陷 |
| 2 | 单元测试 18/18 全绿，功能实际却不生效 | 测试 helper 自行塞了 `evidence.available` 键，而 `evaluator.evidence_rate` 的真实产出里**没有**这个键，于是 `available is True` 恒为假 | 改用真实 `score_trace` 输出驱动诊断断言 |

第 2 条值得单独记一笔：**测试通过与功能生效是两回事**。
若断言所依赖的数据结构由测试自己构造，则实现与真实产出脱节时测试不会变红。
此后凡断言「某类输入应产出某种 Finding」的用例，一律从 `score_trace`
的真实输出出发（见 `TestEndToEndWithRealScorer`）。

### 6.3 端到端实证

同一份任务、全程无硬失败，唯一差别是报告里的数字是否带来源：

| 场景 | Q | A | E | C | 关键数字 | 主导失败模式 |
|---|---|---|---|---|---|---|
| A 数字无来源 | 67.50 | 1.000 | 0.000 | 0.875 | 56 个，带来源 0 | `EVIDENCE_FAILURE` |
| B 同一报告补来源 | 93.21 | 1.000 | 0.857 | 0.875 | 56 个，带来源 48 | `UNKNOWN`（无改进信号）|

A 被自主定位后，提案器生成的首个候选为 `prompt.py::coder.require-sources →on`，
假设原文为「真实 run 的 E 只有 0.10（268 个关键数字仅 27 个带来源），
证据率是 Q 的最大失分项」。

**这构成「agent 如何得知改进方向」的完整链路：
确定性打分 → 质量缺陷归类 → 路由至对应候选。**
全过程不依赖 LLM 自评，因此不会出现「模型学会自我证成」的退化路径。

## 7. 一次数据污染事件与修复

执行模拟 benchmark 后，`status` 显示 **accepted 7 / 经验 7 条**，全部由模拟轨迹产生（ΔQ 恒为 +38.1）。后果是：真实轮次中 `Ledger.is_duplicate` 会将这些假设视为「已尝试」而**跳过**，经验库也会把无效结论检索进 Task Harness，系统将携带无效记忆继续运行且无任何提示。

已修复（`benchmark.py` 三处写入点全部增加 `if not is_fake` 守卫），并补充一对**双向**测试：模拟模式不写入 ⇄ 真实模式必须写入。仅测单向不足——「不写」也可能源于流程中途 SKIP，此种情况下测试会假通过。

> 受影响的 10 条台账已备份至 `experiments/_fake_purge/` 并清空。

## 8. 基准数据集选择与样本量规划

### 8.1 关于 RRSI 论文的事实核查

拟用于对外材料前，已对原始出处逐项核对，结论如下：

| 待核查项 | 核查结果 |
|---|---|
| 论文是否真实存在 | **属实**。`RRSI: Regularized Recursive Self-Improvement of Agent Harnesses`，arXiv:2609.24972，2026-09-21 提交，v2 修订于 09-23 |
| 作者与机构 | Peng Xia、Rujun Han、Zifeng Wang 等，Google Cloud AI Research，合作方含 Stanford、Washington University in St. Louis |
| 代码是否开源 | **属实**。github.com/google-research/rrsi，Apache-2.0 |
| 是否使用 "workbuddy benchmark" | **否。8 个基准中无此名称。** |
| "效果提升 11%" | **原文查无此数。** |

论文实际评测的 8 个基准（3 个领域）：

| 领域 | Evolve 集（参与优化） | Held-out（留出） |
|---|---|---|
| Coding | Terminal-Bench 2.1 | SWE-bench Verified（OOD） |
| Agentic workspace | Harvey LAB | JobBench、GDPval、APEX-Agents（均 OOD） |
| Engineering design | EngDesign | Frontier-Eng（OOD） |

论文原文报告的量级（arXiv v3）：

- evolve split **最高 +6.0 分**（Terminal-Bench 2.1：74.2% → 80.2%）
- 5 个 OOD 基准 **最高 +4.3 分**
- 相对平均先验基线 **最多 +12.5%**（`"outperforming the average prior baseline by up to 12.5%"`）
- 策略 token 较无正则化演化 **减少 30%**（2.42M vs 3.80M / trial）

**两点必须提醒，否则会在尽调环节被问倒：**

1. 部分二手报道引用的数字是 **+14.1 / +4.7**，与 arXiv v3 原文的 **+6.0 / +4.3** 不一致。
   差异可能源于版本修订（报道基于 v1）。**对外材料须直接引用 arXiv 原文并标注版本号**，
   不要转引二手报道。
2. "提升 11%" 无法在任何一版原文中定位。若确实需要引用提升幅度，
   应使用原文明确写出的 **"up to 12.5%"（相对平均先验基线）**，并注明其口径。

### 8.2 任务集必须分层，否则无法区分提升与记忆

现有 `experiments/tasks/replay.json` 有 **20 个真实任务**（由历史日志反推而来）。
但历史日志同时是诊断层的输入——若这批任务既用于诊断、又用于 probe、
又用于经验写入，则等同于用作业当考卷，测得的提升无法与记忆效应区分。

因此引入三层划分（`adaptive_runtime/bench_tasks.py`）：

| 层 | 是否参与演化 | 回答的问题 |
|---|---|---|
| Evolve | 是 | 该候选在当前任务上是否更优 |
| ID held-out | 否 | 同分布任务上是否泛化 |
| OOD | 否 | 跨任务族 / 跨环境是否泛化 |

划分依据为 **task_id 的稳定哈希**而非列表下标，保证：
同一任务在任何一次运行中落到同一层（跨轮可比）；
新增任务不打乱已有分层（历史结论可复现）。

按 `evolve 50% / id 20% / ood 30%` 划分现有 20 个任务的结果：

```
evolve     13   REP-002/003/004/008/009/010/011/013/015/017/018/019/020
id_heldout  3   REP-005, REP-007, REP-012
ood         4   REP-001, REP-006, REP-014, REP-016
```

已验证：乱序输入后分层结果完全一致，无跨层泄漏。

**注意**：这三层是同一分布内的切分，因此 `ood` 层**不等于**论文意义上的跨环境 OOD。
要声称跨环境泛化，仍需接入真正的外部基准。

### 8.3 外部基准：最匹配的是 APEX-Agents，但尚未接入

RRSI 论文 8 个基准中，与本仓库「专业交付物生成」定位最匹配、
且公开可下载的是 **APEX-Agents**（HuggingFace `mercor/apex-agents`，CC-BY 4.0）：

- 480 任务 / 33 worlds，覆盖投资银行、管理咨询、法律
- 每 world 约 166 个文件（财报、SEC 文件、合同、slides 模板）
- rubric 判定：共 1948 条二元标准，平均每任务 4.06 条
- 与本项目 `E`（证据率）指标天然契合——rubric 大量涉及「数字是否有出处」

接入需要两项独立工作，本模块**只定义接口、未实现**：

1. **adapter**：把基准任务映射为本仓库的 `query` + `family`；
2. **grader**：把本仓库产物映射回基准 rubric 的二元判定。

在这两项完成前，**不得声称已在外部基准上验证**。
`bench_tasks.external_status()` 会把接入状态显式输出，任何越界声称都可被机器证伪。

### 8.4 硬约束：噪声与成本的乘积

样本量按配对 t 检验近似式 `n ≈ (z_{1-α/2} + z_power)² · sd² / effect²`：

| 配对差值 sd | 检出 ΔQ=5 | ΔQ=10 | ΔQ=15 | ΔQ=20 | ΔQ=30 |
|---|---|---|---|---|---|
| 6.0（原配置假设） | 12 | 3 | 2 | 1 | 1 |
| 15.0（现配置） | 74 | 19 | 9 | 5 | 3 |
| **24.5（实测）** | **189** | **48** | **21** | **12** | **6** |

换算为墙钟（单次 run 65 万 token / 1109 秒，每个配对 2 个 run）：

| n | run 数 | token | 墙钟 |
|---|---|---|---|
| 12 | 24 | 1560 万 | 7.4 小时 |
| 48 | 96 | 6240 万 | 29.6 小时 |
| 189 | 378 | 24570 万 | 116 小时 |

**这条约束是决定性的**：在当前单次 run 成本下，体系只可能对 **≥20 分** 的大改进敏感。
论文量级的 OOD 提升（约 +4 分，相对提升 7%~13%）在此噪声水平下**无法被检出**，
需要 n≈1200 配对，不具备可行性。

因此验证策略不应是「硬跑完整 benchmark」，而是二选一：

| 路径 | 做法 | 适用 |
|---|---|---|
| **A. 降本**（推荐） | 设计轻量任务集，把单次 run 从 65 万 token 降到 5 万量级 | 想真正测出小改进 |
| **B. 降噪** | 提高温度以外的确定性（固定工具返回、缓存检索结果） | 想在当前任务集上测 |

在两条路径完成前，对外只能声称「机制已接通且自检可信」，
**不能声称「已验证 agent 自动变强」**。

### 8.5 降本路径已落地（A 路径实现）

§8.4 的 A 路径已在本仓库实现为**任务成本画像（RunProfile）切换**，不改动闭环任何逻辑。

**实现位置**

| 组件 | 文件 / 符号 | 作用 |
|---|---|---|
| 画像定义 | `adaptive_runtime/bench_tasks.py`：`RunProfile` / `MEASURED_PROFILE` / `LIGHTWEIGHT_PROFILE` | 单 run token/秒画像；轻量画像为 5 万 token / 120 秒（实测的 ≈1/13） |
| 任务生成 | `bench_tasks.py`：`generate_lightweight_tasks(n, seed)` | 确定性生成窄口径定量简报，刻意留 C/E 余量（强制覆盖子问题 + 必须引源） |
| 成本计划 | `bench_tasks.py`：`plan_cost(..., profile=...)`、`lightweight_cost_plan(...)` | 预算估算随画像切换 |
| 可行性证据 | `bench_tasks.py`：`cost_vs_detectability()` | 产出「效果 × 噪声 × 画像」成本对照表 |
| 开关 | `adaptive_runtime/settings.py`：`task_profile`（env `ADAPTIVE_TASK_PROFILE=measured\|lightweight`） | 默认单 run token 估算随之切换；`run_adaptive.py` 的 `--avg-tokens` 默认值已接到 `CFG.avg_tokens_default` |

**为什么留余量**：轻量任务要求「必须覆盖 (a)(b)(c)…」且「至少 N 个来源」——基线 agent 常漏答子问题（C 低）或断言无出处（E 低）。RRSI 闭环若在 evolve 轮吃到这类惩罚，就能在 ID/OOD 上体现真实提升，而非靠任务记忆刷分。

**落地产物**

- `experiments/tasks/lightweight.json`：60 个确定性轻量任务（seed=0），已按既有稳定哈希三层切分（evolve 36 / id_heldout 9 / ood 15，零跨层重叠）。
- `experiments/reports/cost_vs_detectability.json`：成本对照表机器可读版本。

**核心结论（来自 `cost_vs_detectability()`，cap=15M）**

| sd | ΔQ | n | measured 成本 | lightweight 成本 | 落预算？ |
|---|---|---|---|---|---|
| 24.5（实测） | 10 | 48 | 62.4M ✗ | **4.8M ✓** | 轻量可行 |
| 24.5（实测） | 4 | 295 | 383.5M ✗ | 29.5M ✗ | 仍超预算 |
| 15.0（降噪目标） | 4 | 111 | 144.3M ✗ | **11.1M ✓** | 轻量可行 |
| 15.0（降噪目标） | 10 | 18 | 23.4M ✗ | 1.8M ✓ | 轻量可行 |

**含义**：

1. **降本使 ΔQ≥10 的验证在实测噪声下也落预算**（4.8M ≤ 15M）——「验证」从经济上不可行变为可行。一个典型轻量闭环（evolve 8 任务 ×2 reps ×3 轮 + holdout 8×3 轮）= 120 run / 6.0M token / ≈4 小时墙钟。
2. **论文量级的 ΔQ≈4 仍需降噪（B 路径）**：把 sd 从 24.5 压到 ~15 后，轻量画像下 11.1M 才落预算；不降噪时 29.5M 仍超 2 倍。即**降本为必要前提、降噪为加速器**。
3. 实测画像下**任何**效果量级都超预算（全 ✗），这正解释了此前「验证」为何不成立。

**对外口径（未变）**：可声称「降本路径已落地、ΔQ≥10 的验证在预算内可行、机制与判定器自检可信」；在真实多轮 benchmark 跑出过门 ΔQ 序列 + holdout 同步上升之前，**仍不能声称「已验证 agent 自动变强」**。

## 9. 证据边界

| 项目 | 现状 | 原因 |
|---|---|---|
| 自动推进基线（promote） | **不会自动发生** | `version.promote` 强制要求非 system 操作者。系统为自己升基线等同于无锚漂移 |
| 跨任务经验迁移的净收益 | 未单独度量 | 需「注入经验 vs 不注入」的 A/B 对照；当前 harness 覆盖层仅做组装，无独立迁移实验 |
| L3 结构层 | 未启用 | 见 §1 |
| 严格版轨迹对照 | 未实现 | 方案定为 P2，且需要同一任务多次重复执行且有成有败的数据；当前仅有历史单次日志，强行实现只会产生伪造数据 |
| 多轮 benchmark | 管线就绪，未排期执行 | 需按 §5.3 的检出能力确定规模（n≈18 约 11 小时） |

**因此，判断「RRSI 是否真正实现」的正确提问方式不是「代码是否跑通」，而是：**

1. `selftest` 是否 9/9（能拒能收）—— 已完成
2. 真实任务上执行 3 轮，ΔQ 序列是否至少有一轮过门 —— 待排期执行
3. 同期 holdout 是否平稳 —— 待排期执行
4. 人工 promote 后重跑 benchmark，holdout 是否同步上升 —— 待排期执行 + 人工决策

第 4 条是「普遍变强」的唯一充分证据，前三条均为必要条件。
